# M.O RESTAURI — Project Notes

Single-file marketing site for a Florence-based construction/renovation company. No build step, no framework — one static `index.html` with embedded `<style>` and two `<script>` blocks (one plain, one `type="module"`).

- **Entry point:** [index.html](index.html) (~1700 lines)
- **Other pages:** [privacy.html](privacy.html) — standalone Privacy Policy page, same design tokens, linked from the footer and from both forms' helper text. **Italian-only** — not part of the i18n system below (matches the same precedent already set in `lungarno-estate-demo`'s own `privacy.html`). [404.html](404.html) — custom error page, minimal header (logo + lang-switch) + centered message, **is** wired into the i18n system (`404.title`/`404.body`/`404.cta` keys). A file literally named `404.html` at the project root is auto-served as the error page by GitHub Pages/Netlify/Vercel with no extra config. [contatti.html](contatti.html) — dedicated contact page (see "Contact forms" below); unlike `privacy.html`/`404.html` it carries the **full** site header/footer (not the minimal version) and is fully wired into the i18n system, but has its own self-contained `<style>`/`<script>` copied from `index.html` rather than the hero/carousel/accordion/split-text machinery — no GSAP, no scroll animations on this page by design.
- **[i18n.js](i18n.js)** — the Italian/English translation dictionary + engine. See "Bilingual site (IT/EN)" below.
- **Assets:** [images/](images/), [videos/hero.mp4](videos/hero.mp4)

- **SEO/crawl files:** [robots.txt](robots.txt), [sitemap.xml](sitemap.xml) — both reference a **placeholder domain** (`https://www.morestauri.it/`), swap it for the real deployed domain before/at launch.

## Key mechanisms

### Scroll-scrubbed hero video (Hero → Come lavoriamo → Servizi)
The video is not autoplaying — its `currentTime` is driven directly by scroll position, so the whole `.scrollvid-zone` (Hero + Process + Services) plays as one continuous, seamless animated background with no autoplay dependency.

- `.scrollvid-sticky{position:sticky;top:0;height:100vh}` pins the video full-viewport.
- `.scrollvid-content{margin-top:-100vh}` is the negative-margin trick that lets foreground sections scroll *over* the pinned video for as long as the combined content is tall — this works because `header{position:fixed}` doesn't occupy flow, so the zone starts at document y=0.
- **Only one overlay** (`.scrollvid-sticky-overlay`, a single gradient) exists for the entire zone — this was a deliberate fix for an earlier seam bug caused by two separate overlays not matching at their boundary. Do not reintroduce a second overlay on `.hero` or `.process`.
- JS (`type="module"`, `scrollScrubVideo()` IIFE near the bottom): waits for `loadeddata` (not autoplay/`play()` — that was a previous source of "video not playing" bugs), then on scroll computes `progress = scrolled / (zone.offsetHeight - innerHeight)` and lerps `video.currentTime` toward `progress * duration` each `requestAnimationFrame` for smooth (non-jumpy) scrubbing.
- `videos/hero.mp4` is re-encoded with `ffmpeg -g 1 -keyint_min 1 -sc_threshold 0 -bf 0` (every frame is a keyframe). This is **required** — sparse keyframes make arbitrary-seek scrubbing stutter badly since the browser has to decode from the nearest keyframe on every seek. If the video is ever replaced, re-encode it the same way and verify with `ffprobe -show_entries frame=key_frame`.
- Services section was moved *inside* `.scrollvid-content` (last child) specifically so it renders on top of the video instead of a plain color — `background:transparent`, not `var(--bg)`.

### Nav
Nav links (`Come lavoriamo` / `Servizi edili` / `Contatti`) are hidden behind the hamburger at every screen width, not just mobile — this was an explicit, deliberate choice, not a responsive breakpoint bug.

The mobile-nav CTA is `<a href="contatti.html" class="btn btn-primary">Richiesta sopralluogo</a>` inside `#mobileNav`. There's a CSS specificity trap here: `.mobile-nav a{color:var(--text-on-dark)}` (general rule for all links in the drawer) beats `.btn-primary{color:#000}` (both single-class selectors, but the former also matches the tag so it wins), which made the button render as invisible white-on-white text. Fixed with a more specific override: `.mobile-nav a.btn-primary{color:#000}`. If similar `.btn`/`.btn-primary` elements are ever added inside `.mobile-nav`, this override already covers them.

All 6 "Contatti"-ish links across the site (nav item, header CTA "Richiedi info", mobile-nav item + CTA, the "Perché scegliere" stats CTA card, footer "Contatti") plus the new home Contact-section CTA point to `contatti.html`, not `#contatti` — that anchor only still means something within `contatti.html` itself (its own contact section keeps `id="contatti"` for `scroll-margin-top`).

### Bilingual site (IT/EN)
The whole site (except `privacy.html`, see above) is translatable between Italian and English via [i18n.js](i18n.js), a small standalone file included via `<script src="i18n.js">` right after the GSAP `<script>` tag. **Ported directly from the sister project `../lungarno-estate-demo/properties-data.js:275-551`** — same mechanism, different dictionary — so if you fix a bug in one engine, check whether the other project has the same bug.

- **Engine:** `I18N = { it: {...}, en: {...} }` (flat, dot-namespaced keys like `hero.title.part1`, `process.1.spec2`, `form.note.link`) + `getLang()` (reads `localStorage['mo-restauri-lang']`, defaults `'it'`) + `applyLanguage(lang)` (sets `<html lang>`, saves to `localStorage`, walks `[data-i18n]`/`[data-i18n-placeholder]`/`[data-i18n-aria-label]`/`[data-i18n-title]`, toggles `.is-active` on `.lang-switch [data-lang]` buttons, fires a `langchange` `CustomEvent`) + `initI18N()` (applies saved language, wires the two buttons' click listeners).
- **`data-i18n-aria-label` and `data-i18n-title` are M.O Restauri-specific additions** on top of the ported engine — Lungarno's version only needed `data-i18n`/`data-i18n-placeholder`. Used for the WhatsApp icon's `aria-label`, the accordion panels' `aria-label`s, and the Google Maps iframe's `title`.
- **UI:** a `.lang-switch` pill (`<div class="lang-switch"><button data-lang="it">IT</button><button data-lang="en">EN</button></div>`) in two places — the header's `.nav-right` (visible at every width, same reasoning as `.nav-whatsapp`) and inside `#mobileNav`. Styled with this site's own tokens (`--line`/`--accent`), not copied from Lungarno's (which uses its own `--color-ink`/`--color-cream`).
- **Critical ordering constraint — do not break this:** `initI18N()` is called as the **first line** of the plain `<script>` block (before the header/burger/form logic, and well before the `type="module"` script where `splitTextReveal()` lives). This matters because `splitTextReveal()` reads `container.textContent` and rebuilds it into per-word `.sw`/`.sw-in` spans — if i18n ran *after* that split, the correct-language text would never make it into the split, and a later split would destroy whatever `data-i18n` targets were nested inside (see the hero `<h1>` case below). If you ever reorder the `<script>` tags at the bottom of `index.html`, `i18n.js` + the `initI18N()` call must stay before the `type="module"` script.
- **`textContent`-only, never `innerHTML`** (matches the source engine, avoids any injection surface). This has two concrete consequences baked into the markup:
  - Any element that mixes translatable text with a nested icon/`<svg>` had its text pulled out into its own `<span data-i18n="...">` sibling to the icon — e.g. `<button>...<span data-i18n="form.submit">Invia richiesta</span><svg>...</svg></button>`. Putting `data-i18n` directly on the button would wipe the `<svg>` out on every language switch. This pattern repeats across the process-card `<li>` specs, the split checklist `<li>`s, both form submit buttons, both success messages, the header/mobile CTA buttons, and the stats CTA card's label+sub.
  - The hero `<h1 class="split-reveal split-immediate">` has an embedded `<em>partner ideale</em>` and is split into **three** `data-i18n` targets (`hero.title.part1`, `hero.title.em`, `hero.title.part2`) instead of one key on the `<h1>` itself. Known limitation: after `splitTextReveal()` runs (which it does immediately on load, since this heading has `.split-immediate`), those three inner spans get replaced by the split's own `.sw`/`.sw-in` wrapper spans — so a language switch *after* page load will correctly re-render every other heading's text, but **this one specific `<h1>` won't update on a live switch** (it'll keep showing whatever language was active at load, until the next full page reload). Every other `.split-reveal` element keeps `data-i18n` on the outer container itself, so it re-applies correctly on switch — it just loses the word-stagger animation structure for that one element, which is the accepted general trade-off already noted below. Not worth engineering a re-split-on-switch mechanism for this single element.
- **`buildMailtoLink()`'s subject/body stay hardcoded in Italian** regardless of site language, by design — the recipient (M.O Restauri) reads Italian, not the visitor's browsing language. Only the on-page UI translates. One nuance: the `<select id="servizio">`'s selected `<option>` has no explicit `value` attribute, so `option.value` mirrors `option.text` live — meaning if a visitor fills the form in English, the "Servizio richiesto:" line in the resulting email *will* show the English service name (e.g. "Turnkey renovation"), even though the surrounding labels are Italian. Treated as acceptable (same as the free-text "Messaggio" field, which was always going to be in whatever language the visitor typed it in) rather than a bug to fix.
- Switching language after load generally still updates all text correctly, but flattens any already-split `.split-reveal` heading's word-stagger structure back to plain text (loses the reveal animation for that element on a live switch, not on load) — a deliberate, minor accepted trade-off, not a bug.
- **Extending the dictionary:** add the Italian value under `I18N.it`, the English value under `I18N.en`, same key in both, then reference it via `data-i18n="that.key"` on the target element (or `data-i18n-placeholder`/`data-i18n-aria-label`/`data-i18n-title` for those attributes). No build step, no restart needed — just edit `i18n.js` and reload.

### Room Tour ("Tour degli interni") — GSAP accordion gallery
Rebuilt a second time this project. History: originally a pinned/sticky Ken-Burns cycler → briefly a stacked full-height "fade+scale+blur-text" reveal (Ardène-inspired, IntersectionObserver-based, no longer in the code) → **now a hover-driven accordion gallery**, ported from a React + GSAP component the user pasted in chat (`AccordionGallery.jsx`/`.css`, not part of this repo — this site has no React/build step, so it was translated to vanilla JS + GSAP-via-CDN, same visual/interaction behavior).

- Markup: `#roomAccordion.accordion-gallery` containing four `.ag-panel` divs (Soggiorno, Cucina, Camera da letto, Bagno), each with `.ag-panel__frame > .ag-panel__media > img` + `.ag-panel__overlay`, plus `.ag-panel__label` (`.ag-panel__bar` + `.ag-panel__text`).
- JS: `accordionGallery()` IIFE (last IIFE in the `type="module"` script). On hover/focus/click of a panel, `setActive(i)` triggers `applyLayout(true)`, which builds one `gsap.timeline()` that tweens, per panel: `flexGrow` (active panel grows via a ratio derived from `expandRatio=0.52`; math ported verbatim from the source component), `rotateY` (±8° tilt on the non-active panels either side), the media's `x`/CSS vars `--ag-gray`/`--ag-dim` (parallax shift + grayscale/dim on inactive panels — consumed by `.ag-panel__media img{filter:grayscale(var(--ag-gray)) brightness(...)}`), and the label's opacity/x (fades in only on the active panel).
- Default active panel: index 2 ("Camera da letto"), matching the original component's `defaultIndex`.
- **Mobile (≤720px):** the JS still runs (see note below on why), but a `@media (max-width:720px)` block neutralizes it visually with `!important` (`flex:none`, `transform:none`, labels forced to `opacity:1`), turning it into a plain vertical stack of photos with visible captions — no hover interaction attempted on touch.
- Respects `prefers-reduced-motion` (`duration` forced to `0` in `applyLayout` when `reduceMotion` is true — tweens apply instantly instead of animating).
- If more rooms are added, add another `.ag-panel` block inside `.accordion-gallery` — the JS reads panels via `querySelectorAll('.ag-panel')`, no index is hardcoded except the default-active one.
- **Do not reintroduce a `matchMedia('(max-width:720px)')` early-`return` guard in the JS** to "skip mobile" — one was tried and removed. It's fragile: at the moment this deferred module script runs, `window.innerWidth` can transiently read `0` in some environments (confirmed in the Claude Browser pane tool, see Testing notes), which falsely matches the mobile query and permanently skips initialization for that page load. Since the mobile CSS already neutralizes every inline style GSAP sets via `!important`, letting the JS run unconditionally is both simpler and safer.
- **Fixed bug:** the `.ag-panel__label` wrapper (the div holding `.ag-panel__bar` + `.ag-panel__text`) originally had `opacity:0;transform:translateX(-14px)` as its own *base* CSS — but the JS only ever tweens the two *children* (`bar`, `text`), never the wrapper itself. That meant the wrapper stayed permanently invisible on desktop (nothing ever set its opacity back to 1), so **no caption ever showed for any panel, including the active one** — confirmed both via a user screenshot and via `getComputedStyle`/inline-style inspection in this tool. It only appeared to work on mobile because the `@media(max-width:720px)` override happened to force the wrapper's opacity to 1 there. Fixed by moving the hidden-by-default state onto `.ag-panel__bar`/`.ag-panel__text` directly (where the JS actually operates) and updating the mobile/`prefers-reduced-motion` overrides to target those same two elements instead of the wrapper. **If you ever add a new animated sub-element inside `.ag-panel__label`, make sure its initial/hidden CSS state lives on the exact element GSAP targets, not a non-animated ancestor** — this class of bug (CSS hides the parent, JS animates the child) is easy to reintroduce.

### Contact forms — dual-channel WhatsApp/Email submission (no backend)
There is now exactly **one** real contact form on the site: `#contattiForm` on [contatti.html](contatti.html). `#heroQuickForm` (in the hero, `index.html`) is a second, separate `<form>` with the same fields — the old duplicate at the bottom of the home page's Contact section (`#contactForm`) was **removed** (FASE 3 of the review pass); that section now only shows address/phone/WhatsApp/email/map plus a `contact.home.cta` button linking to `contatti.html`.

Both remaining forms submit via **two explicit buttons instead of one**, wrapped in a `.form-actions` div: `<button type="button" data-channel="whatsapp">` and `<button type="button" data-channel="email">` (both intentionally `type="button"`, not `submit` — there is no native form submission anymore, the `<form>` element only exists for its `checkValidity()`/`reportValidity()` API). Shared logic (duplicated verbatim in `index.html`'s plain `<script>` block and in `contatti.html`'s own inline script — see "Style/workflow preferences" below for why it's duplicated, not shared):

- `buildMailtoLink(form)` — unchanged from before: builds `mailto:restaurisrl@hotmail.com?subject=...&body=...` from `FormData`.
- `buildWhatsAppLink(form)` — new, same field-reading pattern, builds `https://wa.me/393207579541?text=...` with a `Label: value` message (same phone number as `.nav-whatsapp`/the Contact section's WhatsApp row). Pattern (label:value lines joined, then `encodeURIComponent`, then `window.open(url, '_blank', 'noopener')`) is lifted from `../../website_transukro/assets/js/main.js` (`buildMessage()` + the `quoteForm` submit handler around lines 65-121) — that project's version reads *all* form fields generically via a `data-message-intro`/label-lookup helper; here it's hardcoded to this form's fixed 5 fields instead, since there's no need for the generic version.
- `wireContactForm(form)` — attaches a click listener to both `[data-channel]` buttons: on click, `form.checkValidity()` (if invalid, `form.reportValidity()` and stop — same native browser validation bubbles as before), otherwise builds the right link for that button's `data-channel`, opens it (WhatsApp in a new tab, email via `window.location.href`), adds `.sent` to the form, and shows the success message.
- CSS: `.contact-form.sent .form-row,.contact-form.sent .form-actions{display:none;}` hides the fields and buttons once sent (replaces the old, now-removed `#contactForm.sent`/`button[type="submit"]`-keyed rules — those broke when `#contactForm` was deleted and the submit buttons became `.form-actions` instead).
- The success message copy is a **single neutral message** covering both channels ("Si aprirà WhatsApp o il tuo programma di posta...", `form.success` key) — deliberately not two separate per-channel messages, to keep the JS and i18n dictionary simpler.
- Both forms' `.form-note` still says the data is handled per the [Privacy Policy](privacy.html) and links to it — do this for any new form field/copy change too, since it's the GDPR-relevant disclosure point.
- This was an explicit user choice (WhatsApp + mailto, two buttons the visitor picks between, over signing up for a form backend like Formspree/Web3Forms). If that ever changes to a real backend, the email path is the one to swap (`window.location.href = buildMailtoLink(form)` → a `fetch()` call); the WhatsApp path has no backend equivalent to swap, it's inherently a deep link.

## Mobile "video scroll non c'è / foto fuori misura" — root-caused and fixed
This was reported early in the project and stayed unresolved/inconclusive for a while (multiple investigation passes found the Hero video and most photos rendering correctly, and chalked a small ~7-8px horizontal gap up to a testing-tool artifact). A later, more rigorous re-test — loading the page with the mobile viewport already active *before* first paint (not resizing an existing desktop-loaded tab, which left stale JS-computed values around) — found a **real, reproducible bug**, since fixed:

- **Root cause:** the accordion gallery's `accordionGallery()` JS (see Room Tour section above) computes `--ag-media-size` as a square sized off the container's *width*, tuned for the desktop layout (narrow-tall panels in a row). On mobile the same panels are wide-short (stacked column), so the JS-computed square media (e.g. ~190×190px) ended up *smaller than the panel* in both dimensions — each room photo rendered as a tiny, badly-cropped sliver floating in a mostly-empty black box. This is very likely exactly what "le foto sono fuori misura" was describing.
- **Fix:** the `@media (max-width:720px)` block for `.ag-panel__media` now forces `top:0;left:0;width:100%;height:100%;transform:none` with `!important`, overriding both the base desktop CSS and any inline styles GSAP sets — on mobile the image simply fills its panel via the existing `object-fit:cover` on the `<img>`, no JS-computed sizing involved at all.
- **The scroll-video itself was re-confirmed working correctly** on mobile (correct element size, `object-fit:cover`, correct progress-from-scroll math) — the "video scroll non c'è" half of the report was very likely this same photo issue (Room Tour looking broken) being described loosely, or the well-documented rAF-freeze tool artifact (see Testing notes) masking a working feature during an earlier check.
- **The remaining ~7-8px `scrollWidth` vs `clientWidth` gap is real but harmless and isolated**: only `position:fixed;left:0;right:0` elements (`<header>`, `.mobile-nav`) show it; `<main>` and everything inside it (all real content) measure exactly `0` overflow. This matches a known behavior of desktop-Chromium mobile *emulation* reserving a scrollbar gutter that affects fixed-position containing-block width calculation — real phones use overlay/zero-width scrollbars and shouldn't exhibit this at all. Don't chase this further unless a real device screenshot shows an actual visual problem from it (at most it'd be a few px of the header's own solid-color background past the edge — not content clipping).

## Testing notes

- Local dev server assumed at `http://localhost:8811/` (used during the session via the Claude Browser pane's `preview_start`).
- The in-app Browser pane has a recurring artifact where the tab reports `document.visibilityState:"hidden"`, which freezes `requestAnimationFrame` and silently blocks `video.currentTime` seeks and screenshots from reflecting real state. Don't trust a single screenshot/seek test in that tool if results look wrong — cross-check with `getComputedStyle`/DOM state, or open a fresh tab and screenshot immediately with minimal prior interaction. This artifact is inconsistent, not universal: when reverse-engineering the Ardène reference site, an instant `scrollTo` jump did *not* trigger its IntersectionObserver-based reveals even after a round-trip delay (likely that site's own rAF/IO gating on visibility); but the same instant-jump-then-inspect approach *did* correctly trigger our own site's IntersectionObserver reveals (confirmed via `classList`/`getComputedStyle`, then a follow-up screenshot showed the settled state fine). Moral: always confirm via DOM/computed-style before concluding a scroll-triggered animation "doesn't work" in this tool — a stale screenshot alone is not evidence of a bug.
- `ffmpeg` is installed via Homebrew for any future video re-encoding needs.
- **GSAP tweens with `duration > 0` visibly "don't animate" in the Claude Browser pane tool** when the tab reports `document.visibilityState:"hidden"` (the same recurring artifact) — GSAP's ticker depends on `requestAnimationFrame`, which doesn't tick under that condition, so a real hover-triggered `.6s` timeline appears frozen mid-tween no matter how long you wait between tool calls. This is *not* evidence of a real bug: manually draining GSAP's clock with `for (let i=0;i<40;i++) gsap.ticker.tick();` in a `javascript_exec` call forces the same tween to interpolate correctly toward its real end values, proving the timeline itself is configured correctly and only the tool's rAF is stalled. Zero-duration tweens (`duration:0`, used for instant/initial-layout application) are unaffected since they don't need the ticker. Use the `gsap.ticker.tick()` trick to verify any future hover/scroll-triggered GSAP animation here instead of trusting a live screenshot.
- Also re-confirmed in this same debugging pass: `window.innerWidth`/`document.documentElement.clientWidth` can transiently report `0` in a freshly navigated tab in this tool, self-correcting a few tool-calls later (e.g. after a `screenshot` or `tabs_select` call) — see the Room Tour note above on why JS must not gate behavior on a single width read at module-eval time.
- **The Claude Browser pane's tab cache can get stubbornly stale for `i18n.js`/`index.html` across a long session** (many navigations to the same local `http://localhost:8811/...` URLs) — a `navigate` reload, and even a `cmd+shift+r` keypress, can keep serving an old cached response (confirmed once mid-FASE-3: a tab kept showing pre-FASE-1 markup, em dashes included, long after the file on disk was fixed). `fetch(url, {cache:'no-store'})` from `javascript_exec` always proves what's actually on disk/served. To force a genuinely fresh load in the *same* tab: append a throwaway query string to the **page** URL (`index.html?v=2`) — this reliably busts the page's own cache entry — but a same-named `<script src="i18n.js">` is a separate cache entry the query-busted page URL does *not* invalidate; if only script content (not page structure) looks stale, either open a brand-new tab (`tabs_create`) and navigate fresh there, or patch the live page for that one check via `fetch('/i18n.js?bust='+Date.now(),{cache:'no-store'})` + `new Function(code+'; return I18N;')()` + `Object.assign` into the existing `I18N.it`/`I18N.en` objects (redeclaring `const I18N` via `eval` does *not* overwrite the page's real global in this tool's sandboxed eval context — confirmed it silently no-ops instead of throwing). None of this reflects anything a real first-time visitor would experience; it's purely an artifact of hammering the same dev URLs for hours in one browser profile.
- **For mobile testing, set the viewport (`resize_window`) *before* navigating, then navigate/reload, rather than resizing an already-loaded desktop tab.** This mattered concretely: JS that measures element sizes once at load time (like the accordion gallery's `measure()`) and only re-measures via `ResizeObserver` can end up with stale desktop-computed values if the tab loaded at desktop width and was resized afterward, since `resize_window` (a CDP-level viewport override) doesn't reliably trigger the same `ResizeObserver`/`resize` callbacks a real user resizing a real window would in this tool. A true "load fresh at mobile size" test caught a real bug (see the mobile photo-sizing writeup above) that an earlier "load at desktop, then resize" test had missed.

## Style/workflow preferences learned this project

- User writes requests in Italian; mixes in occasional English. Keep responses matching their language when replying about this project.
- User prefers being asked to clarify with a specific screenshot/section name over guessing when a reported visual bug can't be reproduced.
- Prefer sourcing real photos (e.g. via live Unsplash search) over guessing photo IDs blindly.
- When the user says something like "same background as X," confirm interpretation for anything structurally ambiguous (color match vs. literal element/zone reuse) — this caused one rework earlier (Services section background).
- When asked to "recreate" an effect from a reference site, inspect it first (DOM structure, inline styles/transforms, computed styles) rather than assuming from a name or a quick screenshot — the Ardène "Villa Lumière" animation turned out to be a one-shot IntersectionObserver reveal (fade+scale+blur-text), not a continuous scroll-scrub like our own hero video. Confirming this before writing code avoided building the wrong mechanism.
- For a structurally significant change (e.g. replacing a whole section's scroll mechanism), ask which of 2-3 concrete options the user wants before implementing, once "Auto Mode" is off — a quick `AskUserQuestion` with a "recommended" option framed first works well and the user answers decisively.
- The user sometimes pastes a full React component (e.g. a GSAP-powered gallery from a component library) and says "let's use this animation for X" — they want the *visual/interaction behavior*, not literally React in this project. Port the logic to vanilla JS, add the animation library via CDN `<script>` if needed (acceptable here — no build step, but a plain external `<script>` tag is fine), and keep the same math/easing/timing constants from the source rather than approximating them.
- When asked for an honest opinion/audit ("è finito? manca qualcosa?"), the user wants the real unfiltered list, including launch-blocking problems (e.g. forms that don't actually send anywhere) — not just cosmetic polish suggestions. They then want to batch-answer clarifying questions (form backend choice, real vs. placeholder content, which items to defer) up front via `AskUserQuestion`, then have everything approved implemented in one pass rather than checking in after every item.
- For anything requiring a real account/credential the assistant can't create on the user's behalf (GA4 property, Formspree, etc.), wire up a clearly-marked placeholder plus a one-line instruction on exactly what to swap and where, rather than blocking the whole task on it.
- For content the assistant can't responsibly fabricate (real client reviews, real project photos for a before/after gallery, real business stats), ask directly whether the user has it now or will supply it later — don't silently invent numbers/testimonials, and don't silently drop the feature either without saying so.
